# KAGI XR：A／B方式の学習・比較・分担検証仕様

更新日：2026-10-14 JST。目的：別のAIに渡しても、制作の目的・現在地・手順が変わらない引き継ぎ。

## 0. 最初に読む結論

- **A：高品質2D人物＋立体空間演出。** 顔の魅力を保った絵・演奏用パーツを使い、Three.jsの奥行き・軌跡・遮蔽・光・カメラで空間を成立させる。
- **B：Charakuruでリグ・ボーン付き3Dアバターを制作し、既存MIDIで演奏させる。** Tripoによる形状制作、Blenderによる調整とVRM出力、その後の演奏制御までが一続きの検証対象。
- 3Dモーションリファレンスは、2D画像を3Dモデルへ変換するサービスではない。そこで学ぶ奥行き・物体の動き・カメラの関係は、AにもBにも使える。
- **先に両方の学習・仕様整理を終え、その後にClaude CodeがA/B両方を分けて検証する。** 未読のまま新しい方式へ実装を切り替えない。
- ユーザーは追加費用を避けてAを進めてきた。Bの調査・検証の依頼は、Tripo購入・クレジット消費・外部への人物素材送信を無条件に許可するものではない。

## 3. A／Bを同じ土俵で比較する

|項目|A：2D人物＋立体演出|B：リグ付き3D人物＋立体演出|
|---|---|---|
|顔の基準保持|元絵を使える。ただし変形・照明・切り抜きで崩れ得る|生成・テクスチャ・形状を原画と照合する必要|
|カメラ|人物が破綻しない範囲。演出の空間へ進む構成が有効|形状が整えば側面・回り込みも検証できる|
|手・演奏|握り素材、腕パーツ、変形設計が必要|指ボーン、ウェイト、握り姿勢、IK／clipの調整が必要|
|キット|画像だけでなく厚み・打面・前後関係を設計|人物とは別にキット形状・配置が必要|
|光と影|元絵の固定光と舞台光の整合を取る|同一空間で計算できるが、材質・MToon等の扱いが必要|
|費用|既存素材・ツールで進められる部分が多い。作業時間は掛かる|キット自体と外部生成の料金を分けて確認|
|ライブ入力|既存MIDIの受け口に2D動作と演出を接続|同じ受け口に骨格制御と演出を接続|
|iPhone性能|重い透過・粒子・高解像度画像で負荷は増える|ポリゴン・骨・材質・物理・影を含む実機測定が必要|
|現在の証拠|候補23の方向へ本人の限定的な好評あり|今回のCharakuruでKAGIモデルを作った証拠はまだない|

**旧TripoSRの失敗をCharakuruの失敗と同一視しない。逆に、Charakuruの紹介動画をKAGIモデルの成功証拠にも使わない。** 過去の「3D化は顔が崩れる方向にしか働かない」という断定は引き継がない。方式ごとの結果は実物で比較する。

## 4. 共通の保全仕様

1. 元MIDIのノート・順序・時刻・velocityを保持。表示を良くするために入力データを書き換えない。
2. 判定窓±50/100/140ms、得点100/70/40、extra−25、回避+20、debounce60ms、和音30ms等は既存正本と照合し、方式比較のために変更しない。
3. D=2秒、F=1.2秒の記録は残すが、Dの起点・意味の不一致は未解決。合算や追加待ち時間を勝手に導入しない。
4. MIDIと音声を分ける。演奏者と観客の音色、音・映像・判定の時刻は統合検査で確認する。
5. 公開・本番設定を変えない。8765、18765、18767、8766、18768等の既存保護ポートを停止・横取りしない。
6. 額縁システムは独立した既存系統。人物の周りの装飾枠やホームページのクラゲと混同しない。
7. 候補23の演出と保存版を保持する。A/Bは別ディレクトリ・別の安全な確認経路に置く。
8. 静止画、記録MIDI動画、実入力、iPhone参加、販売成立の合格を別々に扱う。

## 5. 同条件の比較素材

- 本人が見た目の基準とするV8原動画と原画像を実見し、ファイルを固定する。
- 本人の正しい握り・交差・肘の参考区間を既存資料から確認。IMG_8583の前半誤例／後半正例を混ぜない。
- 同一10秒の記録MIDI、同一初期構図、同一出力寸法をA/Bに使う。
- 入力が違う比較、カメラが違う比較にはその旨を注記。見た目の差と演奏の差を混同しない。
- テストは、固定正面、制限カメラ、全体演出の三つを分ける。Aに対応外の真横を要求して一方的に不利にしない。

## 6. Aの検証手順

1. 握りが成立する人物素材を確認。顔・手・棒・肩袖の関係を同じ全体画面で見る。
2. 人物とキットの前後、床との接地、紫経路の意味を合わせる。
3. 打撃に応じる軌跡を実際の深さを持つ形で作り、近景と遠景の遮蔽・移動量で奥行きを示す。
4. 人物の平面が露出しないカメラ経路を使い、全景→軌跡の空間→全景をつなぐ。
5. UIと判定到着が見えなくならないことを確認する。
6. 部品が改善しても全体が後退していれば統合版は不合格。

## 7. Bの検証手順

1. Charakuruの構成、ライセンス、外部料金・送信先、既存環境・ポートを学習・確認する。
2. 起動・生成に必要な未承認事項があれば、対象・金額・画像・送信先を具体化して確認する。承認がある範囲だけ実行。
3. 頭部と体の参照を固定し、候補を本人が選ぶ。顔の不採用を骨格の成功で押し切らない。
4. 仕上がったモデルのボーン・ウェイト・VRM情報を検査し、腕・手首・必要な指が扱える状態にする。
5. 左右の手にスティックの固定位置を設け、握り姿勢を作る。棒先から逆算した手首目標と、肘の曲がる方向を定義する。
6. 既存MIDIの読み取り側に演奏制御を接続。楽器→左右手の選択→準備・接触・戻りをIK／clipで制御する。
7. 打点・左右交差・連打・同時打ち・velocity差・休符・停止再開を同じモデルで検査する。
8. Three.js側でVRMを読み直し、材質・揺れ・骨格姿勢が制作画面と一致するか確認する。
9. iPhoneで実機負荷と演奏応答を確認してから、配信系への採否を決める。

MIDIには未来の打撃が含まれないため、予備動作をいつから開始できるかは既存の観客向け時刻設計に従う。入力直後に「既に振り上げていた」ことを無条件に再現できるとはしない。この問題をB独自の遅延追加でごまかさない。

## 9. 合格と停止の条件

|検査|合格の見方|失敗時の対応|
|---|---|---|
|本人らしさ|顔・髪・衣装・比率が基準を維持|背景を豪華にして隠さず人物へ戻る|
|握り|指が棒を保持し、手首と棒の関係が全区間で自然|開いた手への棒重ねを完成としない|
|打撃|同一イベントの棒先が指定打面へ対応|IK到達数だけで自然さを採点しない|
|立体感|前後・厚み・接地・視差が整合|単に色や粒子を増やさない|
|カメラ|全景と見せ場が連続し、人物・UIを壊さない|対応外の角度・近接を制限する|
|保全|既存判定・時刻・再挑戦・配信の回帰なし|不具合を残して本番へ進めない|
|性能|対象iPhoneで決めた負荷・応答条件を満たす|品質設定と構図を両立させる|
|費用|承認範囲内で履歴と残高を把握|超過前に停止、勝手に追加購入しない|

完成率の恣意的な点数や「AIが良いと言った」だけで決めない。本人の採否と、版・範囲・残差を対応付ける。

Claude 品質仕様書 v1

0. この文書について

作成 2026-11-10 ／ 対象 kaginight リポジトリで動く Claude Code（Fable 5.2 ほか） ／ 版 v1

鍵山喬一の報告「直すところと直さないところがある」「ここを直してと言うと他を壊す」「やるなと言ったことをやる」「以前の指示を覚えていない」に対して、何が分かっていて、何をリポジトリに入れたかを残す。

区分は 3 つ。確認済＝出典のページを開いて読んだ。言い回しが違う＝出典はあるが、広まっている言い方と中身が違う。未確認＝この環境から出典に届かず、確かめられなかった。未確認のものは根拠に使っていない。

1. 結論

  1. 指示は会話に置くと消える。圧縮や別セッションで消えるのは、会話の中だけで伝えた指示。リポジトリ直下の CLAUDE.md は毎回読み込まれ、圧縮後も読み直される（確認済）。だから絶対指示は台帳としてファイルに置いた。
  2. 文章の決まりは「守るかもしれない」まで。公式の説明でも CLAUDE.md は強制ではなく文脈。例外のない決まりはフック（機械の関所）に入れるのが公式の推奨（確認済）。だから禁則・回帰検査・終了前の監査をフックにした。
  3. Claude Code は Fable 5.2 を medium で動かす。API の既定は high。公式は、長い作業の途中で終わる現象が low と medium で起きやすいと書き、難しいコーディングと長い作業に high を勧めている（確認済）。だからこのリポジトリの設定を high にした。
  4. 要約を信じず差分を読む。公式の実験（「このコードベースはあなたのもの」という所有の一文を入れた条件）で、ついでのリファクタリングを禁じる一文があっても余計な変更が残り、終わりの要約は小さな変更を書き落とした。公式の勧めは「要約だけでなく差分を見る」（確認済）。このリポジトリの指示には所有の一文を入れていない。そのうえで、終了前に差分と要件を突き合わせる段と、実装者以外のレビューを入れた。
  5. 「Fable 5.2 は物忘れする・雑」という公式の発表はない。あるのは未確認の利用者報告だけ。公式の資料はむしろ「決まりを書かれた通りに守る」と書いている。原因を断定せず、仕組みの側で塞いだ。

2. 症状と、入れた対策

症状（鍵山の報告）仕組みとして言えること入れた対策
以前の指示を覚えていない会話だけの指示は圧縮・別セッションで消える。CLAUDE.md は残るCLAUDE.md ＋ 絶対指示の台帳 .claude/STANDING_ORDERS.md（取り込み）。訂正を受けたら同じターンで台帳に追記
直すところと直さないところがあるmedium では途中で終わりやすい。終わりの要約は当てにならないeffort を high に。終了前フックが「要件ごとに 済／未 と証拠」を求める
ここを直すと他が壊れる文章の決まりは強制ではない。公式の実験でも、条件によっては範囲を限る一文があっても余計な変更が残った（7 章）回帰検査 tools/check_invariants.py（落ちていたら終了を差し戻す。同じ落ち方につき 3 回まで）。差分の突き合わせ。実装者以外のレビュー
やるなと言ったことをやる文章の決まりは強制ではない機械で止められる禁則はフックで止める（操作前に遮断）。そのほかは台帳に理由つきで残す
急に質が落ちる判定に触れると別のモデル（Opus 5／Opus 4.8）へ自動で切り替わり、そのまま続くswitchModelsOnFlag: false（対話できるときは切り替える前にたずねる）
同じ失敗の繰り返し失敗の記録がどこにも残らない失敗台帳 .claude/FAILURE_LOG.md。直近 8 件を開始時に読み込ませる。依頼のたびに「訂正なら同じターンで追記」の決まりを添える

3. 作業の型（最重要）

実装 → 実装者デバッグ → 他者コードレビュー → 本番反映。どんな内容でもこの順を通す。

  1. 実装: 依頼を番号つきの要件に分ける。触るのは要件に必要な箇所だけ。
  2. 実装者デバッグ: 自分で動かす。回帰検査と基盤スキルの検査を走らせる。
  3. 他者コードレビュー: critical-reviewer に依頼文と差分だけを渡す。指摘は「この状況で、こうすると、こうなるからダメ」。NG は直して再レビュー。
  4. 本番反映: OK のあと。レビュー後に変更を足したら、足した分をもう一度レビューする。push・公開・貼り付けは、その操作ごとに鍵山の明示の一言があってから。

この仕組み自体もこの型で作った。レビューの各回の判定と、指摘ごとに直した内容は 9 章に残した。

5. 鍵山さんがやること

  • 直らなかったら、そのまま言う。言い方は自由。訂正だと分かれば、失敗台帳に 1 件追記する決まりになっている。追記されたかは、報告か .claude/FAILURE_LOG.md で確かめられる。
  • 「今後ずっと」の指示は「台帳に入れて」と言う。.claude/STANDING_ORDERS.md に 1 件足される。機械で確かめられるものは回帰検査にも入る。
  • 報告は「要件ごとの 済／未」を見る。未や未確認が正直に書かれているかが判断の材料になる。
  • 手元のアプリが古いと別の問題が出るという利用者報告がある（7 章）。claude --version と claude update で版を確かめる。

6. 効く範囲と限界

  • この仕組みは kaginight リポジトリで動くセッションに効く。ほかのリポジトリ、claude.ai の普通のチャットには効かない。そちらは同じ内容を各リポジトリの CLAUDE.md か、アプリの個人設定に入れる必要がある。
  • フックは、リポジトリが 1 つのクラウドセッションと手元の Claude Code で動く。プロジェクト内のクラウドスレッドと、複数リポジトリのセッションでは、リポジトリのフックは読まれない（確認済）。その場合も CLAUDE.md の決まりは文章として残る。
  • フックが止められるのは機械で判定できるものだけ。「クラゲを変えない」のような中身の禁則は、検査に足せる形（残すべき文字列など）にしたものだけ機械で守れる。
  • 回帰検査は、検査に書いた事実しか守らない。公開中のサイト本体はこのリポジトリの外（index.html は転送だけ）なので、サイト本体の回帰は対象外。
  • ほかのチャットを常時見張る機能はない。同じ台帳をすべてのセッションが読む、という形で揃えている。
  • 訂正かどうかは機械では判定していない（言葉の一致で判定する方式は、試験で見逃しと誤反応が多く、やめた）。訂正のターンに失敗台帳へ本当に追記されたかも、機械では確かめていない。
  • レビューの OK と push は、機械ではつないでいない。命令の文字列を見て push を止める関所を一度作ったが、commit 文に push という語があるだけで commit を止め、別の経路の push は通す、という欠陥がレビューで見つかり、外した。レビューを通すことと、push の前に鍵山の一言を待つことは、文章の決まり（台帳 O-01・O-07）で守る。レビューを受けたかは終了前の監査がたずね、外に出る操作を待つことは依頼ごとの型が毎回添える。
  • 禁則の名前の関所は、うっかりを止めるもの。名前を書かずに親フォルダごと一覧する、といった回り道までは止められない。逆に、名前を含むシェルの命令・検索・エージェントへの依頼は、このリポジトリ内の文書に対するものでも止まる（編集の道具は通る）。
  • 回帰検査の差し戻しは、同じ落ち方につき 3 回まで。差し戻しの文面で「直せないなら落ちている検査をそのまま報告する」よう求める。3 回のあとは、検査が落ちたままでも終了できる。次に監査が出るときは、落ちている旨が監査の項目に加わる。セッションの前から落ちていた場合は、新しいセッションごとに 3 回差し戻される。
  • push の宛先の確認が見るのは、この clone の origin の push 用 URL が kagi920/kaginight で終わるかどうかだけ。ほかの remote への push、git 以外の道具（GitHub の操作など）による push やマージ、別の場所にある clone、ホスト名の違いは見ない。origin がない・git が使えないときは何も言わずに通す。これらは台帳 O-08 の手での確かめで守る。
  • 回帰検査が番人について実際に動かして確かめるのは、名前の関所と、依頼ごとの型の出力だけ。終了前の検査と監査は、該当する記述が残っているかを見るだけなので、中身を骨抜きにする変更までは検出できない。台帳も、項目の見出しが残っているかを見るだけで、本文の書き換えは検出できない。フックを非同期にする設定や、レビュー担当の道具の行への書き足しも検出できない。
  • 終了前の監査は、開始の記録がないセッションでは最初の終了時点を基準にする（それより前の commit は対象外）。差し戻し（回帰検査によるものを含む）のあとに続けて終了するときは監査を出さないので、そのターンの変更の監査は次のターンの終了時に出る。そこでセッションが終われば出ない。git が使えない場所では監査は出ない。
  • モデル自動切替の停止は、対話のない実行（一括実行など）では、たずねる代わりにエラーで止まる。
  • effort を high にすると、出力が増えて消費も増える。戻すには .claude/settings.json の effortLevel を消し、あわせて回帰検査 tools/check_invariants.py の effortLevel の行も消す（検査が high か xhigh であることを確かめているため）。

7. 裏取りの結果

確認済（出典のページを開いて読んだ）

  • Claude Code の既定の effort は Fable 5.2 で medium。API の既定は high。
  • 長い作業で仕事が残ったままターンを終える現象があり、low と medium で起きやすい。公式の勧めは「high から始める」。
  • effortLevel（low／medium／high／xhigh。max は不可）と switchModelsOnFlag は、リポジトリの .claude/settings.json に書ける。
  • 判定に触れた依頼は、生物学なら Opus 5、サイバーセキュリティなら Opus 4.8 でやり直され、その後もそのモデルで続く。
  • CLAUDE.md は開始時に読み込まれ、圧縮後に読み直される。目安は 200 行以内。長いと守られにくくなる。矛盾する指示があると、どちらかが勝手に選ばれることがある。
  • 毎回必ず起きてほしいことはフックに入れる、が公式の推奨。
  • 公式の実験: 所有の一文（このコードベースはあなたのもの）を入れた条件では、ついでのリファクタリングを禁じる一文が同じ指示の中にあっても、約 3 分の 1 の試行で重複コードがまとめられた。所有の一文がない条件では 1 割未満。所有の一文の条件で、終わりの要約は大きな変更は書くが、小さな変更をよく落とした。「要約だけでなく差分を見る」。
  • 公式の実験: 最後まで続けさせる文面を入れると、medium で、仕事を残して終わるセッションが約半分になった。出力は約 3 割増えた。

言い回しが違う（貼られた資料の主張と、原文の差）

  • 「完遂条件を明示すると未完了が半減」 → 半減は本当だが、効いたのは完遂条件ではなく「最後まで続ける」文面。「残りを並べて止まる」終わり方は減らなかった。
  • 「自由に直していいと書くと既存機能を勝手に変える」 → その文言は原文にない。原文は「このコードベースはあなたのもの」という所有の一文の話で、入れると 6〜10 回に 1 回、既存機能の振る舞いが変わった。なお「もっと自由に動け」という一般の指示は何も変えなかった、という記述は別の実験（慎重すぎる振る舞いの話）のもの。
  • 「古い指示への過剰な従属」 → 原文は、積み重なった慎重な指示を忠実に守りすぎて、要らない確認を求める、という話。指示を忘れる・無視するという記述ではない。

1 回目の判定は NG。実装者とは別のエージェントが、依頼文と差分だけを受け取って審査した。指摘と直した内容:

指摘（この状況で → こうなる）直した内容

禁則の対象の名前を、大文字小文字を変える・検索の型に入れる・ほかの道具（GitHub 照会、エージェントへの依頼）で渡すと素通りする大文字小文字を区別しない。すべての道具の、すべての文字列の引数を見る。編集系の道具だけはパスだけを見る
訂正の検知が「直っていない」「やり直し」「消すな」などを拾わず、「ミステリアスに」「違うデザイン案」「壊れにくい構成」に反応する1 回目のあと言い回しを増やしたが、2 回目のレビューで不十分と判定（下）。言葉の一致で判定する方式をやめた
別のフックが一度差し戻したあとは、回帰検査が落ちていても終了できてしまう回帰検査は毎回必ず走らせる。差し戻しは同じ落ち方につき 3 回まで
開始前からあった変更や他人の commit を「このセッションの変更」として監査させる。監査のあと同じ中身を commit すると、もう一度監査が出る開始時点の状態を記録し、監査対象から外す。一覧に「開始前から変更あり」と印を付ける。指紋をファイルの中身から作るので、commit では変わらない
開始の記録がないセッションでは、追跡済みファイルの編集が監査されない記録がなければ、最初の終了時点の commit を基準として記録する（それより前の commit は対象外。6 章）
UTF-8 でないバイトや日本語のファイル名で、監査が黙って抜ける／検査が異常終了する差分の文字列を読まず、ファイルの中身を直接ハッシュする。ファイル名はそのままの形で受け取る。読み取りは壊れた文字を置き換えて続ける
想定外の入力（JSON でない、型が違う、git がない）で異常終了する入力の型を確かめる。想定外の例外は「止めない」終了にする
失敗台帳の F-01・F-02 の原因が、記録にない推定なのに事実として書かれている「記録なし」に直した

1. 結論

  1. 公式 OAuth apps は、社内ツールが個々のユーザーの代理として tailnet を操作するための仕組み。OAuth 2.0 の authorization code flow（RFC 6749 4.1 節）を使い、Tailscale が出す同意画面でユーザーが承認する。アクセス制御・監査ログ・台数の枠は、共有のサービス ID ではなく同意した本人に掛かる。
  2. 公式 いま案内されている使い道は 1 つ: デバイスの登録（scope は auth_keys:create:once）。同意 1 回で使い切りの auth key が 1 つ出る。
  3. 公式 OAuth clients とは別物。clients は client credentials flow で、人のいない自動化向け・タグ所有。apps は人が同意する・ユーザー所有。
  4. 考察 kaginight リポジトリには Tailscale を使っている箇所がない（2026-11-18 に tailscale|tailnet|TS_AUTHKEY|tskey|TS_OAUTH を大文字小文字を区別せず全ファイル検索して 0 件）。調べたのはこのリポジトリだけで、ほかのチャット・ほかのリポジトリ・クラウド環境の設定は調べていない（未確認）。「入れる」が何を指すかも鍵山に確認していない。今回入れたのはこの解析文書だけ。
  5. 考察 OAuth apps が効くのは「複数の人がいる tailnet で、誰のデバイスかを 1 台ずつ本人に結びつけたい」場面。利用者が 1 人の tailnet では利点が小さく、client secret を保管しコールバックを受ける仕組みを持つ負担のほうが大きい。AI のチャットやクラウドの作業環境を tailnet につなぐ用途には、本人の全権限が乗る OAuth apps より、タグで権限を絞れる方式（OAuth clients、タグ付き auth key）のほうが最小権限にしやすい。

2. 仕組み（公式の記述）

公式 2 段構え。管理者が Tailscale API で OAuth app を作り（手順 1〜2）、開発者が自分のツールに認可の流れを実装する（手順 3〜6）。

手順だれが内容
1 作成管理者POST https://api.tailscale.com/api/v2/tailnet/-/oauth-apps。項目は name、redirectUris、scopes（auth_keys:create:once）、任意で allowedNodeAttributes（custom: で始まるものだけ）。応答に id と clientSecret（形は tskey-app-<clientID>-<secret>）。secret は作成時にしか返らず、後から取り出せない。
2 確認管理者GET …/tailnet/-/oauth-apps/<app の id> で scope と redirect URI を確かめる。
3 認可 URLツールhttps://login.tailscale.com/a/oauth_authorize に client_id、redirect_uri（登録したものと完全一致）、scope、state（推測できない一意の値。CSRF 対策）、response_type=code を付ける。
4 同意ユーザー承認すると redirect_uri?code=…&state=… に戻る。拒否すると ?error=access_denied。ツールは先に state の一致を確かめる。
5 交換ツールPOST https://api.tailscale.com/api/v2/oauth/token に grant_type=authorization_code、code、client_id、client_secret、redirect_uri（手順 3 と同じ値）。allowedNodeAttributes を使うなら node_attributes をカンマ区切りで渡す。応答は access_token、token_type: Bearer、expires_in: 3600。
6 登録ツールaccess token がそのまま auth key になる（別の API 呼び出しは不要）。tailscale up --auth-key=<access-token>。

トークンの性質

  • 公式 refresh token は返らない。
  • 公式 有効期限は 1 時間（3600 秒）で、変更できない。
  • 公式 使い切り。期限内でも、最初に成功した使用のあとは拒否される。
  • 公式 デバイスを 1 台足すたびに、ユーザーは同意画面をもう一度通る。

登録されたデバイス

  • 公式 同意したユーザーの身元をそのまま引き継ぐ。そのユーザーを指すアクセス制御の規則が適用され、監査ログはそのユーザーに帰属し、そのユーザーの台数枠を消費する。管理コンソールではそのユーザーのデバイスとして出る。
  • 公式 許可リストに入れた custom: 属性をデバイスに付けられ、device posture の条件や grants から参照して「どう登録されたデバイスか」でアクセスを分けられる。

3. 必要なものと制限（公式の記述）

  • 公式 tailnet の Owner か Admin の役割。
  • 公式 OAuth app を API で作るための、admin scope を持つ API access token。
  • 公式 OAuth app と、それを通して承認する全ユーザーが同じ tailnet に属すること。別の tailnet のユーザーは使えない。
  • 公式 実装する人に、authorization code grant の知識と、HTTP リダイレクトとトークン交換を扱えること。標準の OAuth ライブラリが少ない手直しで使えるとされている。
  • 公式 同意画面は Tailscale が出すもので、見た目を変えられない。

4. OAuth apps と OAuth clients の違い

観点OAuth apps（authorization code）OAuth clients（client credentials）
デバイスの所有ユーザー所有タグ所有
身元同意した個人サービス ID（タグ）
アクセス制御ユーザーの規則タグの規則
監査ログ個人に帰属タグ／サービスに帰属
台数枠承認したユーザータグ
人の関与毎回、同意画面なし（人がいなくても動く）
作り方API（admin scope の API access token）管理コンソールの Trust credentials ページ
secret の持続（考察）secret＋ユーザーの同意＋code が揃って 1 回分secret だけで 1 時間のトークンを何度でも取れる

公式 上 5 行は公式の比較表。「人の関与」「作り方」の 2 行は 2 つのページの記述を並べたもの。最後の 1 行は記述から導いたまとめで、公式の文言ではない。

公式 OAuth clients の注意: 作ったユーザーが tailnet から外れても、その OAuth client は動き続けてトークンを出し続ける。OAuth client から作る auth key は必ずタグ付き。access token は 1 時間で、変更できない。

5. セキュリティの解析

5.1 設計として強い点

  • 公式 共有の auth key やタグの auth key から、ユーザーごとの承認に移す用途が挙げられている。どのデバイスも承認した本人までたどれる。
  • 考察 client secret が漏れても、それだけではデバイスを足せない。ユーザーの同意と、その同意で出た code が要る。OAuth clients の secret（単独でトークンが取れる）より、漏れたときの被害が小さい。
  • 考察 トークンが 1 時間・使い切り・refresh なしなので、盗まれても使える窓が狭い。先に正規の登録に使われていれば無効。
  • 考察 scope が auth key 1 個の作成に限られ、このトークンで tailnet の設定（ACL、DNS など）を読む・書くことは、読んだページの範囲では案内されていない。

5.2 気をつける点（この状況で、こうすると、こうなる）

状況こうするとこうなる対策
OAuth app を作る段admin scope の API access token を長い期限のまま残す・チャットや履歴に貼るこのトークンは OAuth app より強い。漏れると tailnet の管理操作に使われるチャットに貼らない。期限を短くする・済んだら失効させるのが望ましいが、期限を選べるか・失効できるかは未確認
client secret の置き場ブラウザに配る JavaScript、公開リポジトリ、静的サイトに入れる誰でも読める。漏れた secret を止める手順（削除・失効・作り直し）は未確認公開されない場所だけに置く。静的サイト（GitHub Pages など）単体では持てない。redirect URI に http://localhost を登録できるかは未確認で、登録できない場合は交換を行うサーバー側の部品が要る
コールバックstate を確かめずに code を交換するCSRF。攻撃者の用意した code を被害者のツールに通される公式どおり、推測できない state を毎回作り、戻りで一致を確かめる
コールバックcode や token が URL・アクセスログ・Referer・画面に残るaccess token を使用前に読まれると、本人の身元でデバイスを 1 台足される。code だけを読まれても、交換には client secret が要るので登録はできない（code と secret の両方が漏れた場合は成り立つ）HTTPS のみ。code は受け取ってすぐ交換。ログから query を落とす。コールバックのページに外部の読み込みを置かない
登録tailscale up --auth-key=… をシェル履歴やプロセス一覧に残す同じ機械の他の利用者に見える（使用後は無効だが、使用前に読まれると先に使われる）発行したらすぐ使う。共有の機械では打たない
同意する人が Owner／Adminその人の身元でデバイスを足すデバイスはその人のアクセス制御をそのまま受ける。届く範囲がその人と同じになるcustom: 属性を付け、grants／device posture で「この経路で登録されたデバイス」の届く先を絞る。絞りたいならタグ所有（OAuth clients）を選ぶ
AI のチャット／クラウド作業環境を tailnet につなぐOAuth apps で本人所有のデバイスとして登録するその環境から、本人が届く機械すべてに届く。環境が乗っ取られたとき（読み込んだ文書に仕込まれた指示など）の被害が本人の全範囲になる使い捨て・タグ付き・届く先を 1 つに絞った登録にする。OAuth apps は「誰のものか」を記録する仕組みで、権限を狭める仕組みではない
redirect URI広い・古い・使っていない URI を登録したままにするその URI を握った者が code を受け取れる（secret がなければ交換はできないが、守りが 1 枚減る）使う 1 本だけを登録する。照合は完全一致

考察 この表は「こうなる」「対策」とも Claude の判断。state の確認と secret の安全な保管だけは公式ページにも書かれている。
